# v0.1 Scope Decisions

This is the current implementation scope for `coss-svelte`. It resolves the broad COSS inventory into a SvelteKit-native first release plan.

Use this file to answer:

- What is stable in v0.1?
- What is experimental?
- What is deferred?
- Which decisions are already locked?
- Which gaps belong in the post-v0.1 backlog?

For the reasoning behind each decision, read [Decision Records](./decision-records.md). For the 90% to 100% parity gap, read [Post-v0.1 Parity Backlog](./post-v0.1-parity-backlog.md). For skipped or partial work during implementation, read [Unimplemented Components And Parity Gaps](./unimplemented-components.md).

## Scope Principle

The first release should be broad, clean, and idiomatic for SvelteKit.

It should preserve COSS's visual language, naming model, and copy-and-own ergonomics where they help developers. It should not recreate React/Base UI behavior when Bits UI already provides a Svelte-native primitive, or when the behavior would require brittle custom interaction code.

## Locked Decisions

| ID | Area | Decision | Implementation Consequence |
| --- | --- | --- | --- |
| ADR-001 | Public API | Use COSS-facing names over Svelte/Bits internals. | Export names such as `DialogPopup`, `SelectTrigger`, and `SheetPanel`; use Svelte props, snippets, and bindings. |
| ADR-002 | Styling | Use `cn-*` placeholder classes plus one COSS default theme. | Source stays readable; registry output can resolve classes; `packages/theme/src/style-coss.css` is required for package users. |
| ADR-003 | Forms | Native-first core with optional adapter examples. | `Form`, `Field`, and `Fieldset` own semantics and presentation, not app-wide validation. |
| ADR-004 | Registry | Hybrid package plus registry, package-first. | `coss-svelte` is the usable package; registry JSON is generated from the same source. |
| ADR-005 | Date Picker | Keep Date Picker in stable scope through Bits UI. | Public values follow Bits UI and `@internationalized/date` in v0.1. |
| ADR-006 | High-risk custom components | Require explicit behavior contracts before promotion. | Drawer, Sidebar, and Toast are experimental; Number Field is stable behind tested numeric, accessibility, locale, and form contracts. |
| ADR-007 | Particles | Port only MVP particles first. | Full COSS particle parity is post-v0.1 work. |
| ADR-008 | Verification | Use component-family gates. | Presentational, Bits-backed, compound, and custom components need different tests. |
| ADR-009 | Catalog additions | Land later upstream roots as complete vertical slices. | Context Menu joins stable scope with package, registry, docs, example, theme, and interaction contracts together. |

## Experimental v0.1 Components

Experimental components can be exported and demonstrated, but their docs must describe the missing behavior clearly.

| Component | v0.1 Shape | Missing For Stable |
| --- | --- | --- |
| Drawer | Dialog-backed edge panel with trigger, popup, handle, title, description, content, footer, close, focus handling, escape, and outside-click dismiss. | Drag gestures, snap points, nested drawers, drawer menu variants, mobile physics, and responsive dialog/drawer switching examples. |
| Sidebar | Provider-controlled app-shell surface with functional collapse toggles and compound navigation parts. | Persistence, complete collapsed mode, mobile drawer mode, keyboard shortcut policy, final layout tokens, and broader browser coverage. |
| Toast | Basic provider/manager-backed live-region surface with add and dismiss behavior. | Queue and timing policy, updates, pause-on-hover, action focus, anchored viewports, promise helpers, dedupe/upsert, and swipe gestures. |

## Deferred From Stable v0.1

| Item | Reason | Later Path |
| --- | --- | --- |
| Full Drawer parity | Gesture and snap-point behavior requires a custom interaction system. | Run a Drawer interaction spike after stable overlays pass browser tests. |
| Full Toast parity | Toast is a lifecycle manager, not just a visual primitive. | Design a provider/store API and stabilize it with browser tests. |
| Full particle parity | The COSS particle catalog is large and should not drive API churn before primitives settle. | Track MVP, later, and unsupported particles per component. |
| CLI installer | The registry shape must prove itself before install/update automation. | Build after registry output is validated in a clean SvelteKit app. |
| Multiple style presets | The first pass needs one coherent COSS style. | Add only if real use cases require it. |
| Core Superforms/formsnap adapters | Form stack choice is app architecture. | Document optional recipes after core form semantics are stable. |

## Resolved Implementation Questions

| Question | Resolution |
| --- | --- |
| Package name | Use `coss-svelte` for the UI package in this workspace. |
| COSS part naming | Keep COSS-facing names such as `Popup`, `Panel`, `Trigger`, and `Item` where they map cleanly. |
| Theme delivery | Package users import the theme CSS; registry users receive resolved component output. |
| Docs examples | Keep one executable example per implemented component in `apps/www`, importing through the public package surface. |
| Experimental exports | Export experimental components from the main package for now, while metadata marks them as experimental. |
| Lint and format | Use Biome only. Do not add ESLint or Prettier. |

## Not In v0.1

The following work should not be pulled into v0.1 unless the implementation can stay clean and tested:

- React render-prop compatibility.
- Exact Base UI prop and event compatibility.
- Pixel-perfect COSS website parity.
- All COSS particles.
- Full mobile gesture behavior.
- Dedicated form-library dependencies in core.
- A registry install/update CLI.
